# WP-15 — Versioning + Changelog Automation

## Goal
Replace ad-hoc tag cutting with `release-please` driven by conventional
commit messages. Every push to `main` produces a release PR that bumps
`Cargo.toml` version, regenerates `CHANGELOG.md`, and (on merge) tags a
new release + triggers `signed-release.yml` + `release-sbom.yml`.

## Why now
Phase 3 produced `v0.2.0` manually (`git tag -a`, then `gh release create`).
WP-12's signed-release pipeline works; what it lacks is **automation**.
Every release after v0.2.0 should be:

1. **Triggered by PR merge to main** (no human "tag this" step).
2. **Semver-derived from commits** (`feat` → minor, `fix` → patch, `feat!` → major).
3. **Documented in CHANGELOG.md** automatically, grouped by type + scope.

## Deliverables

| File | Purpose |
|---|---|
| `.github/workflows/release-please.yml` | Runs `googleapis/release-please-action@v4` on every push to `main`; opens/updates a release PR. On merge, the action creates a tag and the chained `signed-release.yml` + `release-sbom.yml` fire. |
| `.github/workflows/ci-commits.yml` | PR + push linter enforcing Conventional Commits 1.0. Uses `wagoid/commitlint-github-action@v5` for PR titles and `commitlint/cli` for pushed commits. |
| `.github/release-please-config.json` | release-please configuration: single-package, rust release-type, `CHANGELOG.md` path, scope-aware grouping. |
| `.commitlintrc.json` | commitlint rules: max header 100 chars, allowed types `[feat, fix, perf, refactor, docs, test, build, ci, chore, style, revert]`, scopes `[cli, ptx, obs, bench, fuzz, deps, release, docs, hygiene, ci]`. |
| `docs/WP-15-VERSIONING.md` | (this file) WP deliverable doc. |
| `CHANGELOG.md` | Auto-regenerated by release-please on first release. |

## Semver mapping

release-please's default Rust release-type uses these commit-message rules:

| Commit type | Bump |
|---|---|
| `feat` | minor |
| `feat!` (breaking) | major |
| `fix` | patch |
| `perf` | patch |
| `refactor` | patch |
| `revert` | patch |
| `docs`, `test`, `build`, `ci`, `chore`, `style` | none (excluded from changelog by default) |

Scopes (`feat(cli): ...`, `fix(ptx): ...`) become CHANGELOG.md section
headers automatically.

## Branch-protection dependency

The release PR created by release-please must **bypass** the WP-14
required `ptx / governance` check (or the check must pass on the release
PR's contents). Two acceptable patterns:

1. **Exclude bot PRs**: branch-protection rule:
   `required_status_checks.strict_mode: true` + release-please PRs
   authored by `github-actions[bot]` are exempted.
2. **Re-run ptx on release PR**: WP-14's `ptx-gate.yml` already runs on
   PRs targeting `main` regardless of author, so the release PR will
   trigger it. release-please's PR is content-bumping `Cargo.toml` +
   `CHANGELOG.md`, both in scope.

We adopt pattern (2) — simpler and self-documenting.

## Local-dev workflow

```bash
# Conventional commit (one-liner)
git commit -m "feat(cli): add wp-list subcommand"
git commit -m "fix(ptx): handle missing manifest_path gracefully"

# release-please will pick this up on the next push to main
git push origin feat/wp-foo
gh pr create --base main
# merge PR → release-please opens release PR
# merge release PR → tag pushed → signed-release.yml fires
```

## Acceptance criteria

- [ ] `gh pr merge` of any `feat:` / `fix:` PR to `main` produces a
      release-please PR within 30 seconds.
- [ ] Merging the release PR cuts a tag matching the conventional-commit
      semver bump.
- [ ] `CHANGELOG.md` is regenerated with one section per scope, commits
      grouped under `Features` / `Bug Fixes` / `Performance`.
- [ ] `signed-release.yml` + `release-sbom.yml` fire on the new tag
      without further human action.
- [ ] `ci-commits.yml` rejects PRs with non-conventional titles.
- [ ] No more manual `git tag` / `gh release create` for any version
      ≥ v0.3.0.

## Migration notes

v0.2.0 was tagged manually before WP-15 shipped. release-please will
recognize it as the latest tag and base the next release (v0.3.0)
on all commits between v0.2.0 and the release PR. No retroactive
CHANGELOG.md migration needed — release-please generates the file from
scratch on the first release-please-driven release.

## Out of scope for WP-15

- **Workspace split (WP-16)**: 22 member crates → 4 release groups. WP-15
  treats the repo as a single package; per-crate versioning is WP-16.
- **Coverage + mutation (WP-17)**: separate WP.
- **Dependabot auto-merge (WP-18)**: separate WP.
