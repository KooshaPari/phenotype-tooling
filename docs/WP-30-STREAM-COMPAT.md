# WP-30 — Stream-Cross-Grade Compatibility Tests

## Goal

Closes the "stream versions move independently" gap. With WP-25 introducing 3 release streams (core / cli / ops), each stream version moves on its own cadence. Consumers (users + CI integrations) need assurance that a `cli-stream` release isn't broken by an `ops-stream` bump, and vice versa.

The WP-30 test matrix asserts: for every cross-stream edge in the WP-26 dependency graph, the downstream stream's API contract holds when the upstream stream is at any of {current, current-1, current-2} versions.

## Test matrix

For each cross-stream edge (`from_crate` → `to_crate`) in `.github/cross-stream-dependencies.json`:

```
core @ v0.x  ×  cli @ v0.y  ×  ops @ v0.z
where x ∈ {current, current-1, current-2}
      y ∈ {current-cli, current-cli - 1}
      z ∈ {current-ops, current-ops - 1}
```

Total combinations: 3 × 2 × 2 = **12 combinations per PR**. With 3 cross-stream edges, that's **36 contract assertions per PR** — runs in <2 min.

## Deliverables

### `scripts/stream_compat_matrix.py`

Generates the 12-version matrix, runs each combination in an isolated cargo workspace, and emits a pass/fail matrix.

### `crates/phenotype-cli/tests/stream_compat.rs`

Integration test that asserts the 3 cross-stream API contracts at the type level:
- `phenotype_cli::run_cli()` (cli-stream) accepts the current `dag-scheduler` Args (core-stream) without breaking.
- `hook_entry` (cli-stream) successfully invokes `phenotype_tooling_observability::metrics::init()` (unassigned → cli-stream via sub-dep).
- `phenotype_cli::obs_cmd::run()` calls `phenotype_tooling_observability::metrics::serve()` with the contract established in WP-09.

### `.github/workflows/stream-compat.yml`

PR trigger. On every PR that bumps `core-stream`, runs the matrix. Fails the PR if any non-current core-stream version breaks a downstream stream's tests.

### `docs/WP-30-STREAM-COMPAT.md`

This file.

## Rationale

| Why test cross-grade? | Why a 3×2×2 matrix? |
|---|---|
| Consumers pin one stream but consume from others. They need to know that N-1 core versions back, cli still works. | 3 core versions back catches >95% of regressions (industry standard for stable APIs); 2×2 for downstream channels is enough for tier testing. |
| Release-please bumps per stream independently — without cross-grade tests, a core bump could silently break cli consumers. | Failures are unambiguous: each cell is its own cargo workspace so state is fully isolated. |
| WP-29's canary-rollout only catches prod-time breakage; cross-grade catches it pre-merge. | Matches the "fail fast" principle from WP-23 + WP-24 (coverage + mutation gates). |

## Acceptance criteria

1. `scripts/stream_compat_matrix.py` runs the full 12×3=36 cell matrix in <2 min on a standard GitHub runner.
2. Each failing cell produces an actionable error: which stream, which version, which test failed.
3. The PR comment posted by the workflow includes a markdown table of pass/fail.
4. WP-30 test failures block PR merge (via WP-23's required-check wiring once the workflow is added to `branch-protection/main.json`).
5. After WP-30 lands, any cross-stream consumer can downgrade by 2 minor versions of the upstream stream and have an explicit test guarantee of compatibility.

## Integration with WP-25 (release streams)

The matrix reads `.github/channel-manifest.json` (generated by WP-28's `scripts/channel_manifest.py`) to know the current channel pointers. When a stream-channel release happens, the channel-manifest updates first, then this matrix re-runs.

## Edge cases

- **Pre-1.0 versions**: matrix runs against whatever is in `channel-manifest.json` regardless of major version.
- **Pre-WP-28 state**: if `channel-manifest.json` is missing, matrix falls back to git tags.
- **Single-stream repos**: if a stream has <2 versions in the manifest, the matrix collapses to a single column for that stream (still useful).
- **Cross-stream edges that vanish** (e.g. cli no longer depends on observability): the matrix skips that edge automatically (reads the live WP-26 graph).

## Rollout

- WP-30 first lands in shadow mode: results posted to PR comments but don't block merge.
- After 2 weeks of clean runs (no flaky failures), promote to required-check per WP-23's promotion procedure.
- Threshold: zero failures for full pass. Any failure → PR blocked.
